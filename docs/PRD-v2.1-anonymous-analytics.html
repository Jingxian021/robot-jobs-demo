一页结论 — 先看这六条

  1. 采集不需要注册。访客用随机匿名 ID 与会话 ID 即可完成漏斗分析；注册只解决跨设备收藏，不是数据采集的前提。
  2. GitHub Pages 只够前端。它可以继续托管页面、样式、脚本和看板界面；不能接收事件、写数据库、做服务端鉴权。需要新增后端，但不一定要迁移前端。
  3. 只采优化所需。第一方采集，不接第三方分析厂商；不做营销、广告、用户画像或对外销售；看板只读。
  4. 语言不等于辖区。EN / JA / ZH / DE 是界面语言。Cookie 规则按 IP 国家决定；EN 按国际默认，不因选英文就默认追踪；美国按 IP 单独识别。
  5. 收藏留在本机。收藏职位/公司继续存浏览器，新增一个本机 Saved 页；不做跨设备同步，也不因此要求登录。
  6. 本期 P0 是闭环，不是账户体系。同意管理 → 匿名事件 → 后端存储 → 只读看板 → 据此改页面。邮箱登录与跨设备同步放 P1。

01背景与目标

v1 已经能完成“筛选 → 详情 → 对比 → 去公司官网申请”，但它是纯静态站点： 收藏只在本机，团队看不到哪些筛选、哪些职位、哪次对比真正带来了申请。 现在要补的不是账户体系，而是一条可信的反馈回路。

本期要回答的问题

  • 哪些筛选组合有结果？哪些筛选经常零结果？
  • 用户打开详情前平均用几个筛选？从首页到详情的流失在哪？
  • 对比功能是否真的带来更多外部申请？
  • 不同语言/辖区的用户，在同意选择与核心行为上有什么差异？
  • 哪些职位/公司长期没有申请点击，或频繁被举报过期？

目标（可观察）

ID目标完成证据
G1能看到完整发现漏斗看板可查看“首页 → 筛选 → 详情 → 对比 → 申请点击”的分段转化。
G2数据可用于改版决策每个指标都能对应一个具体动作（见第 8 节），而不是只做展示。
G3拒绝追踪不影响使用拒绝分析后，筛选、收藏、对比、申请跳转全部正常。
G4不引入身份数据本期不收集邮箱、姓名、简历；看板无个人级明细。

02版本边界：v1 的说法只适用于 v1

v1 文档里的“不收集个人数据”“无账户、无登录”，描述的是 v1 的范围，不是对后续版本的永久承诺。 v2.1 仍然不做账户，但会采集匿名行为事件，因此需要更新对外说明。这不是“修订 PII 边界”，而是明确版本差异。

仍然不变的底线：不托管简历、不做站内申请、不做雇主账户、不把数据用于广告、营销或对外销售。

v1 的表述v2.1 的定位需要更新的位置
“does not collect personal data”（v1 范围）v2.1 不收集邮箱或姓名；只收集去标识化的行为事件，用于改进产品。首页 hero、About、隐私政策、页脚
“No account, no sign-in, no profile.”v2.1 仍然没有账户与登录；保存只在本机。Header、Saved 页、页脚
“Nothing personally identifiable.”不收集直接标识；匿名 ID 不跨站、不与身份关联。隐私政策、同意文案
v1 将 accounts / saved-jobs sync 列为 Out of Scopev2.1 仍不在范围；作为 P1 可选能力另行评估。路线图
对外表述 准确说法是：“我们只在您同意后，收集用于改进产品的匿名使用数据；不收集邮箱、简历或申请材料。” 不要笼统地说“我们什么都不收集”，也不要说“完全匿名”却保留可关联的长期标识。

06.1Cookie 与同意管理

FR-CONSENT 目标：按用户所在辖区决定“追踪是否需要先同意”，并让拒绝和接受一样容易。

核心规则 先按 IP 识别国家 → 映射辖区档案 → 再用当前界面语言展示文案。 一个在德国用英文界面的用户仍适用欧盟规则；一个在中国用中文界面的用户不会因此适用美国规则。

辖区档案

档案适用分析默认首层按钮备注
R-EEA 欧盟/德国EEA 成员国关闭，先同意Accept all / Reject all / Customize拒绝与接受同等显著；可随时撤回。[需法务确认]
R-JP 日本日本关闭，先同意Accept all / Reject all / Customize保守默认；匿名统计是否可改为告知+opt-out，[需法务确认]
R-CN 中国大陆中国大陆关闭，先同意同意全部 / 拒绝全部 / 自定义单独同意、数据本地化要求 [需法务确认]
R-US 美国仅按 IP 识别为美国开启，提供退出Accept all / Reject all / Customize；展示 “Do Not Sell or Share”语言不影响档案。[需法务确认]
R-INTL 国际默认 / 兜底EN 国际默认；其他地区；识别失败关闭，先同意Accept all / Reject all / CustomizeEN 只是界面语言，不默认追踪；宁可少采集。

类别

营销无————本期不接入任何广告、再营销或第三方售卖。

横幅与记录

  • 非阻塞，不覆盖内容，不锁定滚动；不要求先选择才能浏览。
  • 三个按钮同等视觉权重；不预勾选；不使用倒计时或“继续浏览即同意”。
  • 提供 Privacy Policy、Cookie 列表与“Cookie settings”常驻入口。
  • 记录：同意 ID、时间、政策版本、识别国家、生效档案、界面语言、类别、操作方式、撤回时间。只存国家代码，不存完整 IP。
  • 同意在 12 个月后、政策版本变更或用户撤回后重新征求 [TBD]。
  • 用户手动声明辖区时，生效档案取“识别结果”和“声明”中更严格的一个。

状态与异常

  • 政策文本加载失败：使用内置当前版本，不回退到过期文本。
  • 拒绝分析后，筛选、收藏、对比、申请全部正常。

06.2匿名数据采集

FR-ANALYTICS 目标：用最少的事件回答“哪里需要改”，并确保同意前不产生任何标识。

标识规则

  • 仅在分析同意后生成随机 visitor_id（第一方作用域）与会话 ID；不使用设备指纹。
  • 不读取或写入邮箱、姓名、简历；不跨站共享；不接入第三方分析。
  • 拒绝分析：不生成 ID、不发送事件；已发送的历史事件按留存规则处理。
  • 用户可在 Saved 页“Privacy”中重置匿名 ID；重置后无法与历史事件关联。
  • 稳定 ID 的留存上限 12 个月 [TBD]；到期轮换。

传输与失败

  • 事件按批发送到第一方后端；失败时最多重试 3 次，仍失败则丢弃并计数，不影响页面。
  • 离线时暂存队列，恢复网络后发送；队列上限 [TBD]，超限丢弃最旧事件。
  • 每个事件必须有事件名、时间、会话 ID；缺少必填属性的破丢弃并记录。
  • 过滤已知爬虫与内部流量；同一事件 ID 去重。
  • 不记录完整 URL 中的敏感参数；筛选状态只记录规范化值。

数据质量

  • 看板显示事件量、缺失属性比例、迟到事件、重复率、最后更新时间。
  • 数据延迟超过 [TBD] 时，指标旁显示“数据可能不完整”。
  • 测试环境与生产环境分离；内部访问不进入看板。

06.3本机收藏页（Saved）

FR-SAVED 目标：让收藏可查看、可清理，但不需要账户，也不做跨设备同步。

入口与结构

  • Header：“Saved (n)”，n 为本机收藏的职位 + 公司数量；为 0 时仍可进入，显示空状态。
  • 页面标签：Jobs / Companies；右侧提供 Export local data 与 Clear all。
  • 页脚固定说明：“Saved on this device only. No account, no sync.”

行为规则

动作规则
收藏职位写入 localStorage；卡片与详情立即显示已收藏。
关注公司写入 localStorage；详情页与 Saved 页显示 Following。

06.4产品优化看板（内部，只读）

FR-DASHBOARD 目标：用一套稳定口径回答“用户在哪一步流失、哪种行为带来申请”，而不是堆图表。

用途限定 只用于产品体验优化：不做运营、营销、广告、用户画像或对外销售。看板只读，不能修改职位、排名或数据。 第一方采集，不接入第三方分析厂商。

09托管与后端：GitHub 够不够？

直接回答 GitHub Pages 够前端，不够后端。不需要为了本期重新托管前端；但必须新增一个能接收事件、写存储、提供看板接口的服务端。 如果只做“假数据演示”，GitHub Pages 足够；如果要真实采集，就不够。

能做不能做

展示静态文档与演示数据保存同意记录、匿名 ID、事件明细

三条可行路径

路径做法优点代价
A 保留 GitHub Pages 托管前端；另建一个轻量后端（事件接口 + 数据库 + 看板接口 + 后台鉴权） 不用迁移站点；前后端独立；最贴近当前现状 需要维护一个后端与数据库；配置跨域与访问控制
B 迁移到同时支持静态页面与服务端函数的平台，前端与接口同一处部署 部署链路更简单；一个平台管理 需要迁移托管；仍要选数据库与配置权限
C 只做演示：GitHub Pages + 假数据看板 最快；零后端成本 不能真实采集；只能用于评审，不能用于优化决策

建议：路径 A。理由：当前站点已经在 GitHub Pages 正常运行，没有必要为了一个轻量采集端整体迁移；把静态站点与数据服务解耦，后续也更容易替换。

后端最小能力

  • 事件接收：校验事件名与必填属性、限流、去重、拒绝未知字段。
  • 存储：事件、同意记录、匿名 ID 映射；按留存规则清理。
  • 看板接口：只返回聚合结果；需要内部鉴权。
  • 管理端：内部邮箱名单、二次验证、角色、审计日志。
  • 隐私：按匿名 ID 删除事件；导出聚合 CSV；不记录完整 IP。
  • 运维：CORS 白名单、HTTPS、备份、监控与错误告警。
